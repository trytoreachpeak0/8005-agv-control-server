# `.GetNewClosure()` 到底携带什么：实测

> **这个目录是 cs#266 那条守卫的唯一依据。** 守卫要判「哪些写法会静默读出空值」，而这件事
> **不能靠读文档或读代码推**——下面有四格的结果与直觉相反，而且**同一条规则在这个仓库里被写错过三次**，
> 三次都是因为只测了一种形状就外推。

**权威是 `result-capture-grid.txt`**（由 `Measure-CaptureGrid.ps1` 产生）。另外三份
`result-*.txt` 是更早的测量，留着是因为它们本身没错、错的是从它们外推出去的结论；见最后一节。

## 结论：只有一条轴，就是「在哪里取闭包」

> **`GetNewClosure()` 对「它被调用的那一个作用域」里的变量做按值快照。** 普通查找能在**父作用域**里
> 找到的名字，不在快照里——**而在同一个位置普通查找是找得到的**，这就是它在评审里看不出来的原因。

| 取闭包的位置 | 文件顶层名（无限定） | `$script:` 限定读 | `$global:` 限定读 | 外层函数的局部／参数 |
| --- | --- | --- | --- | --- |
| **文件自己的顶层**（`.ps1` 与 `.psm1` 一样） | 携带 | **携带** | 运行时解析得到 | 不适用 |
| 函数体内 | **空** | **空** | 运行时解析得到 | **空** |
| 嵌套的 scriptblock 内 | **空** | **空** | 运行时解析得到 | **空** |

每一格都配了对照组（自己的局部、自己的参数，或同一处的直接读），**对照组必须非空**——否则「这一格是空的」
和「我的夹具写坏了」分不开。第一次写这份测量时就是没有对照组，把结论记错了。

另外三格，都在 `result-capture-grid.txt` 里：

- **`foreach` 语句的循环变量**（B8）：携带得到。
- **闭包体【内部】的 `ForEach-Object` 读 `$_`**（B7）：携带得到，那是闭包自己的 `$_`。
- **闭包体直接读【外层】流水线的 `$_`**（A6、B6、C5）：**空**。

## 守卫按这张表怎么判

| 情形 | 守卫 | 依据 |
| --- | --- | --- |
| 读外层函数的变量（从更深作用域取闭包） | **报** | B、C 行 |
| 在函数体内读文件顶层名或脚本参数 | **报** | B2、B5 |
| 在函数体内做 `$script:` 限定读 | **报** | B3、C3 |
| 在文件顶层做 `$script:` 限定读 | **不报** | A3、D3 |
| `$global:` 限定读 | **不报** | A4、B4、C4 全部非空 |
| 闭包体直接读外层流水线的 `$_` | **报** | A6、B6、C5 |
| 闭包体内部的 `ForEach-Object` 读 `$_` | **不报** | B7 |
| 变量在取闭包**之后**才赋值 | **不报**（进不确定项） | B9 是空的，但按位置判在循环里会判错 |

## 三条被推翻的旧结论

**每一条都不是外人写的，是这个仓库自己先后写下的。** 列出来而不是删掉，因为它们正是读者会带着来的词。

**一、「嵌套就是空的」——错。** cs#203 只实测了一种嵌套形状（`result-shapes.txt` 形状 2）就外推。
实际上**嵌套但读自己作用域变量的完全正常**（形状 3、7），**不嵌套的反而是空的**——普通 scriptblock 里
（形状 4）、函数内定义的函数里（形状 6）。

**代价量出来了**：把守卫里「收集嵌套 scriptblock 的 `param`」这条规则删掉（相当于按「嵌套」判），
3 个合法夹具立刻误报，**仓库里 11 处正常调用点被报**。一个天天误报的守卫下场是被关掉，**于是连它本来
能抓的那一类也一起没了**——比没有守卫更糟。

**二、「`$script:` 限定读无条件为空」——错。** 这一条是从 `result-module-scope.txt` 的 T5 外推的，
而 T5 是在**模块的函数体内**取闭包。实测（A3、D3）：**在文件顶层取闭包时它是携带得到的**，`.ps1` 与
`.psm1` 都一样。真正的分界还是那一条轴。

**三、「`.psm1` 顶层变量不可捕获」——错。** 这一条从 T1 外推，而 T1 同样是在模块的函数体内取闭包。
实测 D2：**在模块自己的顶层取闭包时携带得到**。不可捕获的是「在该模块的某个函数里读它」——那和表里
其它所有格是同一行。

**这三条有一个共同的形状：每一次都是「测了一种位置，把结论写成与位置无关」。** 所以这份 README 的
规则表按位置分行，而不是按「写法」分类——按写法分类正是三次出错的语法。

## 两种调法的差别（只影响一格，但那一格很重要）

`pwsh -File 脚本.ps1` 时脚本顶层名会落进全局作用域，于是**函数体内的闭包也读得到**（B2、B5 非空）；
用调用运算符 `& 脚本.ps1` 跑时脚本有自己的作用域，读不到（B2、B5 为空）。

**守卫按 `&` 这一种判**，因为 `Invoke-L2Scenario.ps1` 就是这么调场景的（`& $scenarioPath -Context $context`）。
对 `pwsh -File` 直接跑的脚本，守卫因此偏严——这一条写进了守卫的不确定项清单。

**这一格是本票最实际的缺陷来源**：一个场景作者只要把探针从顶层挪进一个辅助函数，`$Context` 就读成空，
判据必然红，60 秒后报成「服务端没干活」——正是 cs#203 烧掉一次真装置时段的那个形状。守卫原先对这个
形状报 0 条。

## 这份清单的边界，明写

**它是「作者想到的那些形状」，不是全集。** 守卫对它解析不了的一律按「不确定 → 当作可见 → 不报」处理，
清单由 `Get-L2ClosureCaptureUnknowns` 导出，可以和「0 条发现」一起打印——**宁可漏报也不要误报**：
一次误报会挡住一张与它无关的票，而被挡的人没有能力自己判断该不该被挡，因为真正的机理要跑完这张网格
才说得清。

**今天 0 个活实例。** 全仓 123 个文件、23 个闭包站点，新旧守卫都是 0 条发现。**所以这条守卫是预防，
不是在修一个现存缺陷**——别把它读成「我们刚修好了什么」。它的判别力由另一件事证明：把 cs#203 修复提交
（`e084d876`）的**父提交**上那份 `L2TaskTypeJourney.psm1` 喂给守卫，**报 2 条、行号 270 与 274**，
正是修复 diff 删掉的那两行，同一文件另外 7 个闭包站点零误报。

## 早期那三份为什么留着

**它们的数字没有一个是错的**，错的是从单一位置外推出去的规则；而那三条错误规则各自在源码注释里活过一段
时间，所以把产生它们的测量留在旁边，比删掉更有用——下一个读到「`$script:` 无条件为空」这句话的人，能在
同一个目录里看到它是怎么来的。

两个已知瑕疵，不改（历史证据不回溯改写），在这里记明：

- `result-cross-file.txt` 第 1 行的**标签**写成了「脚本参数 \CTX」，那是写夹具时被 shell 转义吃掉了
  变量名，应为 `$Context`；**测出来的值 `CTX` 是对的**，而且网格的 A5 重测了同一件事。
- 三份早期结果各自只变了一个轴，单独读任何一份都会得出比事实更强的规则。要读规则，读上面那张表。
