# `real-onboard-expected-action-overdue` 的两次红（control-server#204，条目 1 与条目 3）

两次都在本机真装置上跑，对端是 `24af41e4`（onboard-hmi `w2g/fp-v2-impl`）与 `fb5f7c59`
（slots-simulator `main`），与同一批 CI 绿运行传的是同一对提交。

**服务端那一侧的缺陷提交只在本地，不推远端**：远端历史里混进故意的缺陷提交，日后读 `git log` 的人要多
花一次判断。两份补丁各自存在自己目录的 `DEFECT-PATCH.diff` 里，照着能复现。

## `cs204-eao14-red-no-second-request`：条目 1 的红

服务端 `94c59c8d`（`de29ec16` + 一行缺陷）。缺陷是把 `SafetyStateChanged` 那个触发点关掉——
`OnboardMessageProcessor` 里 `if (await AffectsAnOverdueSlotAsync(...))` 改成 `if (false && ...)`，
于是**第一次告警仍然会让服务端要一份中途快照，而门槛后重开引起的状态变化不再要第二次**。

**14 条判据里只红 `L2-EAO-14`，另外 13 条全绿。**

```
FAIL L2-EAO-14 | 请求 1 / 快照 2 / 端点读数 v10
```

- 「请求 1」：整趟只有第一次告警那一条 `SafetyStateSnapshotRequested`，重开之后没有新的；
- 「快照 2」：握手那份加中途那份，没有第三份；
- 「端点读数 v10」：仍停在中途快照那个版本，没有前进。

**为什么另外 13 条不该红**，逐条说清楚（否则「没红」也可能只是它们对这件事本来就没有判断力）：

| 判据 | 它判的是什么 | 与这个缺陷的关系 |
| --- | --- | --- |
| `L2-EAO-01`、`-02` | 门槛之前：重开发生了、什么都还没有 | 都在第一次告警之前，那时服务端还没被问到要不要再要快照 |
| `L2-EAO-03` | 告警字段与 `raisedAt` | 车载端产的，服务端要不要快照不影响它 |
| `L2-EAO-04`、`-05` | 第一次告警之后的请求、快照与采纳 | **缺陷没有动这条路径**，走的是 `OnboardAlarmSnapshot` 那个触发点 |
| `L2-EAO-06`、`-07`、`-08`、`-09` | 端点一行、读数来自中途快照、看板卡片、HMI 文字 | 都建立在中途那份快照上，而它照常发生了 |
| `L2-EAO-10` | 上报不改变行为 | 守护判据，与快照请求无关 |
| `L2-EAO-13` | 重开后端点仍一行、`raisedAt` 与 `alarmId` 不变 | **不变性**判据：服务端少要一次快照，不会让它多出一行或改掉 `raisedAt`。这正是把活性单开成 `L2-EAO-14` 的理由——两件事坏掉的方式不同 |
| `L2-EAO-11`、`-12` | 期限合成一行、闭环撤下 | 在重开之后，不读快照版本 |

## `cs204-eao11-red-no-redecide`：条目 3 的证据

服务端 `7971fc74`（`de29ec16` + `0004cdf9` 的那一行：中途快照之后不再重判就绪）。

这一次**不是「只红一条」的注入**，它要证明的是另一件事：**判据表是完整的**。同一个缺陷、同一对对端提交，
与 cs#167 当时那份红对照：

| | 判据表 | `L2-EAO-11` | `L2-EAO-12` |
| --- | --- | --- | --- |
| 旧写法 `evidence/l2/20260919-cs167-red-05-no-redecide/` | **11 行** | **不在表里** | **不在表里** |
| 新写法（本目录） | **14 行** | FAIL，带读值 `ONBOARD_SESSION_NOT_READY / 0 行 (no row) / OPEN/EMPTY/0/0` | **PASS** |

差的三行：`L2-EAO-11`、`L2-EAO-12` 恢复，加上新增的 `L2-EAO-14`。

`L2-EAO-12` 这一格尤其值得看：**它在旧写法下永远取不到**。旧写法里场景在第 8 节的等待上抛出、就地中止，
第 9 节（放货关门闭环、撤下）整段不跑，所以这条守护判据在任何超时场合都必然缺席。现在场景走完了闭环，
而且这一条是 PASS——缺陷影响的是就绪重判，不是闭环撤下。

两次运行的 `expectedActionOverdueThreshold` 都是 `00:00:20`，与 `setup.psd1` 一致（条目 2：场景不再自己
写一遍这个值，而是和编排器读同一个文件）。
