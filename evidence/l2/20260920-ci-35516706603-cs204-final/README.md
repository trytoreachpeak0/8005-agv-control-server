## 那次红：同一族缺陷的**第三个窗口**，而且位置与前两次都不同

```
FAIL L2-DA-08  3 connections, 1 open (#1: relay dropped DurableAck; #2: onboard closed; #3: open)
```

`L2-DA-03`、`L2-DA-04` 这次**都 PASS**——连接 #2 的握手完整走完了
（`SessionHello → SessionAccepted → OperationResult → DurableAck → CapabilitySnapshot → … →
RecoveryStateReport → DurableAck → SessionReadiness`），会话回到了 Ready。**断开发生在握手之后。**

#2 尾部（代理流量，时刻取自 `protocol-fault-proxy.json`）：

```
22:35:28.274  >OperationProgress
22:35:28.318  >Heartbeat              ← 车发心跳，等 HeartbeatAck
22:35:28.350  <DurableAck             ← 给上一条 OperationProgress 的
22:35:28.351  <SlotOperationCommand   ← **服务端主动下发，插在心跳与它的应答之间**
22:35:28.541  <HeartbeatAck
22:35:29.084  >SafetyStateChanged     ← 此后服务端再没有回过 ack
22:35:30.331  >Heartbeat
22:35:31.205  >OperationProgress
             连接在 22:35:31.587 被车关掉，2 秒后开 #3
```

**与 control-server#259 是同一个机理——服务端主动下发插进了一个请求-应答对之间——但窗口不同。**
cs#259 现在描述的窗口是「握手完成之前」（`HandshakeCompleted` 为假的那段）。这一次握手早已完成，
插进去的是**心跳的请求-应答窗口**。

所以那道门**不能只加在 `HandshakeCompleted` 上**：车载端在心跳、快照上报等每一个「发一条、读下一行
当应答」的窗口里都同样脆弱。这一点要补进 cs#259。

### 与本票的关系

**不归本票，也不可能是本票引起的。**本票在这条场景里只动了 `L2-DA-09` 那一块（分段计数与注释），
而 `L2-DA-08` 判的是连接数。本票的改动不碰连接、不碰握手、不碰心跳。

三轮真装置的命中率：`35513390399` 撞上一次（窗口一：握手内）、`35516023239` 三次全绿、
`35516706603` 撞上一次（窗口三：心跳内）——**9 次里 2 次**。按工作区规矩，连撞两轮就不再刷第三轮。

## 一个要人拍板的数字：`durable-ack-lost-01` 有一轮只读到 6 个元素

```
干净扫描 73 轮（最少一轮读到 6 个元素）  ← 红的那次
干净扫描 70 轮（最少一轮读到 116 个元素）
干净扫描 67 轮（最少一轮读到 114 个元素）
```

前一轮 run `35516023239` 的三次是 114 / 114 / 113。**所以 6 是个异常值，而且它恰好出现在车载端断开
重连的那一次**——那一刻界面大概正在重建。

按先定的口径，个位数**报上去、不自己改判据**。但要说清这和口径设想的情形不同：它设想的是「树比你
以为的小」，而这里是**同一个界面在同一个场景里，绝大多数时候 114～116、有一瞬间只有 6**。

这意味着 `$read -eq 0` 那条红线**在这一轮不会触发（6 > 0），而那一轮实质上没看到完整的树**。
「读到 6 个元素」被记成了一次干净扫描。更强的下界可能值得加，但取多少仍然不是这几个样本能定的——
**而且真正该补的多半不是下界，是 control-server#260 那条正向锚点**：有锚点的话，「读到 6 个元素、
其中没有锚点」会直接红，不需要猜一个阈值。
