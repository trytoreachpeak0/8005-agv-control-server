# `L2-RW-02` 收紧之后，它的判别力到底有多少（control-server#204，条目 10）

调度审查提出的问题，答案写在这里而不是留给绿运行去暗示：**一次绿运行证明的是「这条判据不误报」，
不是「它有判别力」——一条永远为真的断言在绿运行下的表现和一条好断言完全一样。**

## 一、旧写法（杀完直读）在这条 rig 上会读到什么

**今天恰好读得到正确状态，而且没有任何东西保证这一点。** 不是「必然读到不完整状态」。

证据是 CI run `35513390399` 的 `real-onboard-restart-while-waiting-operator-01`，收紧后的等待每轮都把
读数写进了 journal：

```
inbox-settled  Count=22  StableFor=00:00:00          Rounds=0
inbox-settled  Count=22  StableFor=00:00:00.3073863  Rounds=0
inbox-settled  Count=22  StableFor=00:00:00.5613766  Rounds=1
...
inbox-settled  Count=22  StableFor=00:00:02.0931463  Rounds=2
```

**杀完进程之后第一次读就已经是 22 行，一路 22 到底**，与杀之前的基线相同。也就是说这一次，杀的那一刻
服务端手上没有任何在途的持久报文，旧写法直读同样会读到「0 行结果 / Prepared」。

## 二、那个窗口为什么仍然是真的

「车载端在等操作员时是静止的，所以不会有在途报文」——**这句话是错的，而它是我自己先写下、后来实读
推翻的**。留着这一段不是为了自省：**结论没变（收件箱确实不动），但理由从错的换成了对的，而错的那个
理由会在下一个场景里把人带偏**——换一条车载端会产出持久报文的场景，「静止」那个前提立刻不成立，
而下面「心跳不入库」这个真正的理由仍然成立。

实读两端：

- 车载端在会话期间**每 2 秒发一次心跳**（`WireToGateSessionService.DefaultHeartbeatInterval`），
  它一刻也没有闲着；
- 但**心跳不进收件箱**：服务端的 `OnboardMessageProcessor` 对 `Heartbeat` 直接回一条 `HeartbeatAck`
  就返回，不落 `ProtocolInbox`。所以收件箱行数不变，不是因为车载端没在发，是因为它发的那种东西不入库。

真正进收件箱的持久报文（`OperationResult`、`SafetyStateChanged`、告警快照）在这个时点是**事件驱动**的：
等操作员期间没有事件，所以没有在途。而事件随时可能来——**门的状态动一下、一条告警起落，就有一条**。
这条场景里操作员是在 Kill **之后**才去动门的，所以那一刻恰好关着。

**结论：窗口是真的，只是这条场景的时间线让它几乎总是关着。**「几乎总是」不是「总是」，而判据不该建立在
一个没人保证的时机上。

顺带核过一个巧合：心跳间隔 2 秒与这里等的「稳定 2 秒」同量级，但因为心跳不入库，它不会让等待提前成立，
也不会让它一直不成立。

## 三、为什么没有取红证据

**取不到便宜的红，原因具体，不是「懒得取」。**

要让旧写法露馅，需要同时满足两件事：

1. 车载端在被杀前一刻发出了 `OperationResult`；
2. 服务端还没把它落库。

第 1 件在这条场景里**按设计不会发生**——车载端在 `WAITING_OPERATOR` 时等的是人，不产出结果。所以造这个红
必须注入**车载端缺陷**（改它的代码，让它在被杀前发一条结果），那要改车载端仓、重新发布对端、占一次真装置，
成本远超这条判据本身。

而且按本工作区的规矩，**偶尔不红的红证据等于没有证据**：即使注入了车载端缺陷，「服务端恰好还没落库」这一半
仍然是时机，取出来的红会时红时绿。硬造反而比不造更差。

## 四、那么收紧换来了什么

三件可检查的事实，都写进了判据的「实际」栏：

| | 旧写法 | 收紧后 |
| --- | --- | --- |
| 实际栏 | `0 行 / Prepared` | `收件箱 22 行（杀前 22），稳定 2.1 s，其间运行时转了 2 轮 / 0 行 / Prepared` |
| 落库延迟时 | 读到 0 行 → **绿** | 等到收件箱稳定才读，那时已落库 → 读到 1 行 → **红** |
| 整个服务端不动了 | 读到 0 行 → **绿** | 运行时转不满两轮 → 等待超时带读值 → **红** |
| 退出前就留下过结果 | 读到 0 行 → **绿** | `L2-RW-04` 的「结果只有一条、且晚于重启」→ **红** |

## 五、独立审查改掉了上面两句里的错，记在这里

这一节原本写着两条「下界」：收件箱行数不少于杀前基线，以及运行时又转过两轮。**审查把两条都驳了，都对。**

**「行数不少于基线」恒真，一件事都不证明。**`ProtocolInbox` 只增不减，那个合取项永远成立。它被写进判据、
还被写进 PR 正文当成「区分静置与卡住」的两件事之一——**一条恒真的合取项看起来像判据，读的人会以为那个
方向被守住了，于是对它放松警惕**。已经去掉，杀前行数只留在「实际」栏作诊断。

**「运行时又转过两轮」证明的是 `JourneyRuntimeEngine` 那个循环还在转，不是车载端入站通路还在转。**
入站 TCP 读循环卡死、消息处理器死锁在非数据库的锁上，`mapStationReads` 照样前进。所以它只排除「整个
服务端不动了」这一类，不排除「入站通路死了而引擎还在空转」——而后者恰恰是这条判据最怕的那种。

真正把这件事钉死的是审查给的那条正面判据，已经加进 `L2-RW-04`：**这一次 attempt 的 `OperationResult`
只有一条，而且接收时刻晚于重启。**读的是入站通路的产物本身。`L2-RW-02` 那三个事实保留，但它们各自
声称什么，按上面这一段的说法写，不再多声称。

顺带记一处既有的部分兜底：取那条结果用的是 `@(...)[0]`，**取的是最早的一条**。真要是退出前留下过一条，
`[0]` 拿到的就是它，「结果只有一条」与「晚于重启」两个合取项都会红。这不是刻意设计的防线，但它确实在挡
——写下来免得下次有人把它改成 `[-1]`。
