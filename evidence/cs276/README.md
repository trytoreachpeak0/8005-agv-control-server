## 第一步：定因（step1/）

探针源码以 `.cs.txt` 存档（不参与编译），原始输出与之同目录。

**装置**：真实的 `OnboardTcpServer`、真实的 `OnboardMessageProcessor`、内存 SQLite、合成车载端 `OnboardPeerSession`；两者之间一个字节中继。断电时中继不再往服务端转发任何东西，也永远不关服务端那一侧的 socket（没有 FIN，没有 RST）。服务端写来的字节，要么读走丢掉，要么完全不读、让发送缓冲区堆满。车载端随后重连，失败隔 2 秒再试。判据：新一代会话在 `OnboardPeer` 里可路由，且连续 3 秒不被服务端关掉。

v2 上每次失败的服务端日志都是 `An Onboard peer is already attached for 'AGV-CS276-01'`；旧连接在断电后约 6 秒被 `went silent ... closing it (ADR-cross-0027)` 关掉，下一次重试就成功（读到的）。

## 回归测试的反向验证

新测试类 `tests/ControlServer.Tests/OnboardPowerLossReconnectTests.cs`，两条：S1 形状与 S3 形状。

**判据**（审查后改成按事件判，见 PR #369 的审查意见）：

- 前提：第一次尝试之前旧代次还在路由表里；成功之前至少有一次尝试「握手答完、但不可路由」。
- 旧代次在 30 秒挂死保护之内离开了路由表。
- 此后开始的第一次尝试成功，新会话可路由的时刻也在 30 秒之内，并且之后连续 3 秒不被关。
- S3 另断言断电后至少有一次推送挂了 1 秒以上，证明写确实卡住了。

第一版（`b59b75e5`）用的是 12 秒墙钟上限，那一版的 M1–M3 证据被本目录的新证据覆盖；旧文件仍在 git 历史里。

**绿**（读到的）：`green-run1..3.txt` 连跑三次都是 12/12。每次两条用例的时间线一致：旧代次约在断电后 5.5 秒离开路由表，第 1、2 次尝试（0、约 3 秒）都是「握手答完、但不可路由」，第 3 次（约 6.1 秒）成功。所以**断电后约 6 秒恢复**；step1 探针打印的 9.1～9.3 秒含之后 3 秒的稳定观察，减掉之后也是约 6 秒（见上一节）。S3 断电后最长的一次推送挂了约 5.3 秒。`green-related-with-architecture.txt`：本类、静默失联类、握手门类，加全部 `*ArchitectureTests`，共 90 条全绿，含出站 schema 门禁，退出码 0。
